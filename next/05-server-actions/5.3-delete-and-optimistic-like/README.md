# תרגיל 5.3 · מחיקה ולייק אופטימי

רשימת פוסטים עם כפתור מחיקה שמבקש אישור, ולייק שמתעדכן מיד עם `useOptimistic` וחוזר לערך הקודם כשהשרת נכשל.

## הרצה

```bash
npm install
npm run dev
```

הנתונים נשמרים ב-`data/posts.json` (נוצר בשינוי הראשון ונמצא ב-`.gitignore`). כדי להתחיל מחדש, מוחקים את התיקייה `data`.

**בדיקת כשל:** מריצים `SIMULATE_LIKE_FAILURE=1 npm run dev` ולוחצים על לייק. המספר עולה מיד, ואחרי כשנייה וחצי (ההשהיה המלאכותית ב-action) הוא חוזר לערך הקודם ומופיעה ההודעה "הלייק לא נשמר".

## משתני סביבה

| משתנה | משמעות | דוגמה |
| --- | --- | --- |
| `SIMULATE_LIKE_FAILURE` | כש-`1`, ה-action של הלייק מחזיר כשל (לבדיקת החזרה אחורה) | `1` |

## החלטות מרכזיות

- **`useOptimistic(likes, reducer)`**: בזמן שה-action רץ (בתוך transition), הקומפוננטה מציגה את הערך האופטימי. כשה-transition מסתיים, React זורק את הערך האופטימי וחוזר ל-`likes` שהגיע מהשרת. בהצלחה, `revalidatePath` מביא את הערך החדש; בכשל, ה-prop לא השתנה, ולכן המספר "חוזר אחורה" לבד. אין צורך בקוד שמבטל את השינוי.
- **ה-action מחזיר `{ ok: false }` ולא זורק שגיאה**: שגיאה שנזרקת מ-action של טופס מגיעה ל-error boundary ומפילה את הדף. כשל צפוי מחזירים כערך, ומציגים הודעה קטנה.
- **אישור מחיקה עם `confirm` ב-`onClick` של כפתור ה-submit**: `e.preventDefault()` מבטל את שליחת הטופס, כך שביטול באמת לא קורא ל-action. רק הכפתור הוא Client Component; הטופס עם `deletePost.bind(null, post.id)` נשאר בקומפוננטת השרת.
- **`bind` להעברת המזהה**: מעבירים ל-action ארגומנט קבוע בלי שדה hidden. ה-id עדיין מגיע מהלקוח, ולכן ב-action אמיתי עם משתמשים בודקים הרשאה (ראו תרגיל 6.4).
- **הרשימה בתוך `<Suspense>`**: קריאת הקובץ היא I/O בזמן הבקשה, ועם `cacheComponents` היא חייבת לשבת בתוך Suspense.
