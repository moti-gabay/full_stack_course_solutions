# תרגיל 3.3 · דף פרטים מלא

דף `/posts/[id]` שמושך פוסט מ-JSONPlaceholder. הכותרת והתיאור של הלשונית נוצרים ב-`generateMetadata` מאותם נתונים. פוסט שלא קיים מגיע ל-`notFound()`, ושגיאת רשת מגיעה ל-`error.tsx`.

## הרצה

```bash
npm install
npm run dev                 # http://localhost:3000/posts/1
```

- `/posts/1`: כותרת הלשונית היא כותרת הפוסט.
- `/posts/99999`: דף ה-404 של `not-found.tsx`.
- שגיאת רשת: מריצים עם כתובת API שבורה, ונכנסים ל-`/posts/3`:
  ```bash
  POSTS_API_URL=http://127.0.0.1:9 npm run dev
  ```
  מוצג `error.tsx` עם כפתור "נסו שוב".

## משתני סביבה

| משתנה | חובה | תיאור |
| --- | --- | --- |
| `POSTS_API_URL` | לא | כתובת ה-API. ברירת המחדל: `https://jsonplaceholder.typicode.com`. משמש לבדיקת שגיאת רשת. |

## החלטות מרכזיות

- **פונקציה אחת, `getPost(id)`, משמשת גם את `generateMetadata` וגם את הדף**. היא מסומנת `"use cache"`, ולכן שתי הקריאות באותה בקשה (וגם בבקשות הבאות) מגיעות ל-API פעם אחת בלבד. לא צריך להעביר נתונים בין המטא-דאטה לדף.
- **הפרדה בין "לא קיים" לבין "נכשל"**: על 404 מה-API הפונקציה מחזירה `null`, והדף קורא ל-`notFound()`. על כל כשל אחר (סטטוס לא תקין, או fetch שזורק כי השרת לא זמין) היא זורקת שגיאה, ו-`error.tsx` תופס אותה. אם היינו מחזירים `null` על כל כשל, תקלה ברשת הייתה נראית למשתמש כמו 404.
- **`loading.tsx` בתיקיית `[id]`**. עם Cache Components, ‏`params` הוא מידע של זמן בקשה (אין כאן `generateStaticParams`), ולכן הדף צריך fallback. ה-skeleton נבנה מראש כחלק מה-static shell, והפוסט מוזרם אחריו. בפלט ה-build הנתיב מסומן `◐`.
- **`error.tsx` הוא Client Component** (זו דרישה של Next), ומשתמש ב-`retry()` כדי לנסות לטעון מחדש. ב-production Next לא שולח לדפדפן את הודעת השגיאה המקורית, רק digest, ולכן ההודעה למשתמש כללית.
- **נבדק בדפדפן headless** מול `npm start`: ב-`/posts/2` הכותרת היא `qui est esse`, ב-`/posts/99999` מוצג "404 · הפוסט לא נמצא", ועם `POSTS_API_URL` שבור מוצג "לא הצלחנו לטעון את הפוסט".
